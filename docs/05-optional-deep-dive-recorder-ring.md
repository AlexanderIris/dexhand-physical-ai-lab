# 05 · 专题深挖：非阻塞记录环与“可发现的不完整”

> 本专题深入一处设计、一次实验和一个尚未解决的问题，记录为什么这样设计、做过哪些尝试、发现了什么，以及如何判断结果是否达到预期。

## 1. 我选择深入的问题

**在灵巧手 1 kHz 控制环里，怎样记录每一帧状态，同时保证写日志/发数据不会反过来阻塞控制？如果记录端真的跟不上，怎样让离线训练和调试知道数据缺了，而不是拿到一份“看起来正常”的残缺数据？**

这是我认为灵巧手/数采手套数据闭环里最值得讨论的一处工程取舍：它同时涉及实时性、内存、背压、数据完整性和故障可观测性。

## 2. 最初的朴素方案和问题

最容易写的方案是在控制周期末尾直接写文件：

```c
read_sensors();
safety_check();
compute_and_apply_command();
fwrite(&sample, sizeof(sample), 1, log_fp);
fflush(log_fp);
```

主机 demo 里这样写很简单，但放到灵巧手嵌入式系统中有三个问题：

1. `write()`/`fwrite()`/`flush()` 的耗时受文件系统、eMMC/SD 卡擦写、USB 和网络影响，抖动不可控；
2. 存储或上位机异常时，控制环可能阻塞在记录路径，影响关节周期；
3. 记录失败如果只打印日志，离线数据可能静默缺帧，Physical AI 训练侧无法区分“设备没发生”与“数据没记下来”。

所以我把问题改写成两个独立目标：

- **控制面目标**：记录路径只能占用有界时间，队列满时立即返回，不允许等待 I/O；
- **数据面目标**：任何丢弃、CRC 错误、周期空洞和 writer 错误都必须可计数、可标记、可被离线工具发现。

## 3. 当前设计：SPSC Ring + 异步 Writer + GAP Marker

### 3.1 数据流

```text
dex_control_loop_step()
  → 组装 DexControlSample
  → dex_recorder_submit_control()
      → payload 编码
      → dex_frame_encode() 加帧头/CRC
      → dex_spsc_ring_push()：有界 memcpy + 原子索引
  → 控制环立即继续

低优先级 writer / 测试 drain
  → dex_recorder_drain()
      → dex_spsc_ring_pop()
      → file_writer / USB / 网络 / MCAP writer
```

### 3.2 为什么选 SPSC 固定槽环形队列

- 生产者只有控制任务，消费者只有记录 writer，符合单生产者/单消费者模型；
- 固定槽大小避免动态内存和变长节点分配；
- 入队/出队是定长拷贝和 head/tail 更新，执行时间可预估；
- 主机侧可用 C11 `_Atomic` 验证逻辑，移植到 MCU 时可替换为短临界区或平台内存屏障；
- 队列把控制周期与 I/O 抖动隔离，writer 可以批量落盘。

### 3.3 满队列策略

当前参考实现选择**控制优先**：

1. ring 满时 `dex_spsc_ring_push()` 立即返回 false；
2. recorder 增加 `dropped_frames` 和 `pending_dropped`；
3. 控制环不重试、不阻塞；
4. ring 恢复可用后，下一个控制样本入队前先尝试写 `gap_marker`；
5. 解码器根据控制样本中的 `cycle` 检查周期连续性，并解析 GAP marker。

这里有一个细节：被丢弃的帧没有成功入队，因此文件中已存储帧的 `seq` 仍可能连续；真正能发现控制样本缺失的是**控制周期号 `cycle`**。所以协议同时保留帧序号和业务周期号，二者不能互相替代。

## 4. 我做过的尝试 / 迭代

### 尝试 1：先实现完整二进制帧，而不是直接 dump 结构体

一开始可以直接把 C 结构体 `fwrite` 到文件，但这会带来：

- 结构体对齐和字节序依赖；
- 编译器/平台升级后布局变化；
- 指针、padding 和保留字段语义不清；
- 其他语言难以解析。

因此改成显式小端编码：28 字节通用帧头 + 类型化 payload + CRC16。Python 解码器不依赖 C 头文件内存布局。

**发现**：协议编解码和 CRC 单测能在没有硬件的情况下验证数据格式；篡改 payload 一个字节即可被解码器拒绝。

### 尝试 2：队列溢出时只增加计数

第二版只在 recorder 里维护 `dropped_frames`。这能让仿真器打印统计，但日志文件本身不知道发生过丢弃；如果只把 `.dexlog` 文件发给同事，recorder 的内存计数会随进程退出消失。

因此增加 `gap_marker`：队列恢复后把累计丢帧数、待标记丢帧数和最近周期号写入数据流。

**发现**：数据自描述能力更重要。运行时指标用于实时告警，写入文件的 GAP 用于离线追溯，两者都需要。

### 尝试 3：用故障注入实验验证，而不是只做正常路径

我给主机仿真加了 `--stall N` 参数：前 N 个周期不调用 drain，人为模拟 writer 卡死。

正常实验：

```text
1200 cycles, ring=128
accepted=1202 dropped=0 gaps=0
decoder: missing_cycles=0, CRC=0, completeness=PASS
```

停摆实验：

```text
300 cycles, ring=32, stall=120
accepted=213 dropped=90 gaps=1
decoder: control samples=210, missing_cycles=90,
         gap_markers=1, cumulative_dropped=90, strict exit=1
```

**发现**：

- ring 满后控制线程没有被 writer 拖住，仿真控制路径仍在运行；
- 仅看文件帧数会误以为只有 210 个周期，解码器结合 `cycle` 后能明确报告缺失 90 个周期；
- `--strict` 退出码可用于采集后检查或 CI，避免残缺会话直接进入训练集。

### 尝试 4：把“完整”拆成不同层次

最初容易把“完整记录”理解为零丢失。实验后我会更精确地表达：

- **传输完整**：CRC 正确、帧边界可解析；
- **序列完整**：帧 seq 和控制 cycle 可连续检查；
- **时间完整**：多设备时间戳可对齐且同步质量已知；
- **语义完整**：Schema、单位、固件、标定和坐标系齐全；
- **存储完整**：chunk、manifest、哈希和掉电恢复可信；
- **业务完整**：会话包含预期任务段、安全事件和结束标记。

队列机制只解决其中一部分，不能声称整个 Physical AI 数据闭环已经完整。

## 5. 如何判断结果是否达到预期

### 当前原型达到预期的标准

- `make test` 全部通过；
- 正常仿真日志通过严格解码：无 CRC 错误、无周期缺失、无 GAP；
- `--stall` 实验能稳定复现队列溢出，解码器报告缺失周期和 GAP，并返回非零退出码；
- 控制路径不直接调用文件 I/O，队列满时立即返回；
- README 和验证目录保留真实命令输出，而不是只写“支持高可靠记录”。

### 产品化还需要的判据

- 在目标 MCU 上测量 submit 的最坏耗时和关中断窗口；
- 在真实 writer 卡顿分布下做队列容量规划；
- 验证 eMMC/USB/网络异常、进程重启和随机掉电；
- 测量 ring 内存占用、栈占用和高水位；
- 对 P0 安全事件和 P1/P2 传感器流使用分级队列，避免高频数据挤掉故障事件；
- 用真实手套/灵巧手数据验证时间对齐和训练格式转换。

## 6. 尚未解决、待继续讨论的问题

1. **队列容量与降级策略**：在 RAM 受限的手掌控制器里，应该用多大 ring？当触觉阵列、关节状态和调试 trace 同时突发时，是按话题优先级丢帧，还是给安全事件独立队列？
2. **掉电原子性**：append-only 数据块 + 最后写 manifest/成功标志是否足够？是否需要双 manifest、CRC 链或每条会话的哈希树？
3. **多设备硬同步**：手、手套、IMU、触觉和外部相机之间，优先选择 PPS、CAN sync 还是 PTP？同步质量如何随温度和时钟漂移建模？
4. **MCU 与 MPU 的边界**：哪些数据应在 MCU 侧落盘，哪些应直接送边缘 Linux/上位机？文件系统和 MCAP writer 是否应完全离开硬实时控制器？
5. **“完整记录”的成本**：高频触觉和视频数据全量保存会带来存储、带宽和隐私成本；哪些数据应全量、哪些增量/压缩/触发式保存？
6. **记录与安全的故障隔离**：如果记录芯片过热、文件系统占满或 USB 中断异常，怎样保证不影响电机安全保护，同时把记录子系统故障上报给上层？

## 7. 技术概述（约 2 分钟）

“我最想深入讲的是控制环和记录环之间的解耦。最朴素的做法是在控制周期末尾直接写文件，但文件 I/O 和网络的抖动会反向阻塞控制，而且静默写失败会让训练数据缺帧。我的参考原型把控制样本编码后放进 SPSC 固定槽 ring，控制线程只做有界拷贝和原子索引更新，低优先级 writer 再 drain 落盘。

队列满时控制优先，submit 立即返回并计数；恢复后写一个 GAP marker。这里我特意同时保留帧序号和控制周期号，因为被丢弃的帧没有入队，文件帧序号可能连续，但控制周期号会出现空洞。我做了一个 writer 停摆实验：300 个周期、32 槽 ring、前 120 周期不 drain，最后解码器报告 210 个控制样本、90 个缺失周期、1 个 GAP，严格模式返回 1。

这个实验验证的是机制，不是产品可靠性。还没解决的包括目标板 WCET、真实存储卡顿、掉电 manifest 原子性、多设备硬同步和多优先级队列。后续希望在真实灵巧手和数采手套里继续验证 MCU、边缘 MPU 和上位机之间的记录边界划分。”
